# Roadmap — @gnome-ui/react-native-charts

Component porting plan from [`@gnome-ui/charts`](../charts/README.md) (23 components, built on
Recharts/SVG-over-DOM) to React Native, on top of [Victory Native](https://commerce.nearform.com/open-source/victory-native/)
(Skia + Reanimated) — this package's package.json/`README.md#design-notes` documents why that
library was chosen over `react-native-svg-charts` (unmaintained) or hand-rolling on
`react-native-svg` directly.

This block was tracked as `🚫 Deferred as a block` in
[`packages/react-native/ROADMAP.md`](../react-native/ROADMAP.md) until a concrete need to start it
came up — see that file for the original deferral note.

| Status | Component | Notes |
|--------|-----------|-------|
| ✅ | **LineChart** | First component — established the package's architecture: `matchFont({ fontSize: 12 })` (not `theme.fontFamily`, see README) for axis labels, `getChartPalette(theme)` for series colors, a hand-rolled legend (Victory Native has none built in). No interactive tap tooltip yet — see README |
| ✅ | **BarChart** | Second component — moved the shared architecture (axis font, palette, legend, `InputKeys`/`NumericalKeys` generic helpers) out to `src/internal/` (`ChartContainer`, `ChartLegend`, `chartKeys`, `useChartFont`), now that a second consumer needed the exact same code. Grouped/clustered bars via `BarGroup`/`BarGroup.Bar` (not stacked — matches the web version's default un-stacked `<Bar>` behavior), `roundedCorners={{ topLeft: 4, topRight: 4 }}` for the top-rounded look |
| ✅ | **AreaChart** | Third component — `stacked`/`gradient` toggles, matching the web props. Non-stacked draws `Area` (fill) + `Line` (stroke) per series since Victory Native's `Area` only fills, no stroke; stacked uses `StackedArea` with per-row `areaOptions` for gradient. Gradient fill via Skia `<LinearGradient>` as a child, colors built with a new `withAlpha()` helper (`#RRGGBB` → `#RRGGBBAA`, the same suffix trick `Chip`/`Highlight` use in `@gnome-ui/react-native`). **Real on-device bug found and fixed**: `CartesianChart`'s auto y-domain is each series' own raw-value extent, not aware `stacked` sums them — the stacked chart's topmost band rendered visibly flat-clipped at the un-stacked ceiling until `domain={{ y: [0, stackedMax] }}` was computed and passed explicitly for `stacked` mode |
| ✅ | **PieChart** | Fourth component, first non-Cartesian (polar) chart — `PolarChart`/`Pie.Chart`/`Pie.Slice`/`Pie.Label` instead of `CartesianChart` (no axes/grid at all, `data`/`height`/`donut`/`showLabels`/`showLegend`/`legendPosition` only, no `series`/`xAxisKey`). `PolarChart`'s `colorKey` generic requires the data itself to carry a real (non-optional) color field, so each item is pre-resolved to `{ ...item, resolvedColor }` before handing it to `PolarChart` — no `InputKeys`/`NumericalKeys` replica types needed here since this component isn't generic over consumer data shape. `Pie.Label` draws centered *inside* each slice (`radiusOffset`), a deliberate platform-idiom swap from the web's external leader-line labels — Victory Native has no leader-line primitive and building one wasn't worth it for a label position, not a data question. Kept the web's <4%-of-total label-clutter guard (computed from `slice.sweepAngle / 360`, since Victory Native's own `Pie.Slice` has no built-in equivalent). No inter-slice white border (web's `stroke`) — `Pie.Slice` hardcodes `style="fill"` on a single `Path`, so a stroke would need a second overlaid `Path` per slice; skipped as a minor, deliberate cosmetic trim. First chart shipped in this package with no bug found on the on-device screenshot check |
| ✅ | **RadarChart** | Fifth component — **no Victory Native primitive exists at all** (confirmed: neither `CartesianChart` nor `PolarChart` support an arbitrary-axis-count spider plot), flagged to the user via `AskUserQuestion` before starting rather than assumed; user chose hand-rolling directly on `@shopify/react-native-skia` (`Canvas`/`Path`/`Line`/`Text`/`Skia.PathBuilder`) over the alternative of skipping ahead to a Victory-Native-backed chart. Own manual `View`-`onLayout`-then-`Canvas` sizing (no `CartesianChart`/`PolarChart` wrapper to measure for it). Grid is `GRID_LEVELS` (4) concentric N-gon rings + one spoke line per axis; each series is a closed polygon (`Skia.PathBuilder.Make()...build()` — not the older mutable `Skia.Path.Make()`, deprecated in this Skia version, confirmed via a real runtime warning caught before shipping) rendered twice, fill then stroke, so `filled` toggles only the fill's opacity. Axis labels use `font.measureText(text).width` to manually center/right/left-align per axis angle (mirrors `Pie.Label`'s internal `getFontGlyphWidth` trick, since Skia `Text` has no CSS `text-anchor` equivalent) — no explicit radius-axis tick-number labels (a deliberate, documented scope trim; the web version's own `PolarRadiusAxis` numbers are barely visible anyway). Rendered correctly on the very first real on-device screenshot, no bugs found |
| ✅ | **RadialBarChart** | Sixth component — confirmed via `AskUserQuestion` that hand-rolling on Skia (same approach as `RadarChart`) was still wanted rather than skipping to a Victory-Native-backed chart. Each `data` item is one concentric semicircle ring (`SkPathBuilder.addArc` on an oval sized per ring, stroked with a thick `strokeWidth` band rather than a filled annular-sector path) — a gray full-180° track drawn first, then the value-proportional arc on top in the series color, `strokeCap="round"` for the friendly rounded ends. All rings share one 0-to-max scale (`max` of all `data[].value`, same convention `RadarChart`/the web version use), matching the web's own `startAngle={180} endAngle={0}` half-circle-gauge layout. **Real bug found and fixed via the on-device screenshot**: the arc rendered as a tiny clipped sliver near the canvas's bottom edge instead of a semicircle — the sweep direction was inverted (used `sweepAngle: -180`, tracing the *bottom* half via Skia's `addArc` clockwise-positive/y-down convention, almost entirely outside the canvas since the center sits at the canvas's bottom edge by design). Fixed by flipping to `sweepAngle: +180` (verified the direction algebraically against Skia's own doc comment before re-testing, not by trial and error). **User-spotted follow-up from a pasted screenshot crop**: the gray track's arc ends were square while the value arc's were round — `strokeCap="round"` had only been added to the value `Path`, not the track `Path`; fixed by adding it to both |
| ✅ | **CloudChart** | Seventh component — flagged as "No Victory Native equivalent" in this file, but turned out to need **no Skia canvas at all**, unlike `RadarChart`/`RadialBarChart`: reading the web source first showed it has no real word-cloud packing/collision algorithm — just flex-wrapped `<span>`s with `font-size` scaled linearly by value, laid out by the browser's own text flow. Ports directly to a `flexWrap: 'wrap'` RN `View` of `Text`s, no architecture question needed. Web's `:hover { opacity: 0.7 }` dropped (no touch equivalent, and the words were never interactive — no `onPress` in the source either). `lineHeight` computed per-word (`fontSize * 1.2`) since RN's `lineHeight` is an absolute pixel value, unlike CSS's relative `1.2` multiplier that works uniformly across the source's differently-sized words for free. Shipped with no bug found on the on-device screenshot check — first hand-checked chart since `PieChart` to do so |
| ✅ | **SparkLineChart** | Eighth component — minimal inline chart (no axes/grid/legend/tooltip), reusing `CartesianChart` purely for its scaling math with `axisOptions={{ lineColor: 'transparent' }}` and no `font` to hide every decorative part. Explicit generic type arguments (`CartesianChart<Record<string, number>, '__x', string>`) instead of the `InputKeys`/`NumericalKeys` replica pattern — this component fully controls its own internal normalized-data shape (always a plain `Record<string, number>`, via a synthetic `__x` index field standing in for the web's implicit array-index x-position), so TS infers cleanly without needing that machinery at all. `series`/`dataKey`+`color` dual API ported directly from the web version (`SparkSeries` type included). Web's hover-triggered `highlighted` gradient-reveal mode dropped — deliberately, not silently: a sparkline is typically embedded at a size (e.g. a table-cell-sized inline chart) where no touch affordance reads naturally, unlike this whole port's usual "swap hover for long-press" convention. Default color is `theme.accentColor` (not the chart palette), matching the web's own `var(--gnome-accent-color)` default specifically for this component. Ships `role="image"`+label only when `aria-label` is given, otherwise hidden from the accessibility tree entirely (`accessibilityElementsHidden`) — mirrors the web's own conditional `role`/`aria-hidden`, since an un-labeled decorative sparkline shouldn't be a screen-reader stop at all. Shipped with no bug found on the on-device screenshot check, including the inline-beside-text usage this component is designed for |
| ✅ | **SparkAreaChart** | Ninth component — extracted `SparkLineChart`'s helpers (`resolveSparkSeries`, `normalizeSparkData`, `sparkAccessibilityProps`, the `SparkSeries`/`SparkData` types) into `src/internal/sparkTypes.ts` on this second consumer, same "extract on the second real occurrence" call as `BarChart`'s `src/internal/` split. Fill + stroke layering reuses `AreaChart`'s own recipe (`Area` for fill, a separate `Line` for stroke, since Victory Native's `Area` hardcodes `style: "fill"` and doesn't accept a `style`/`strokeWidth` override — confirmed via a real `tsc` error when first tried as a second `<Area style="stroke">`, not assumed), gradient fill via the same `withAlpha()`-built `<LinearGradient>` `AreaChart` uses. Same dropped `highlighted` hover mode as `SparkLineChart`, same reasoning. Shipped with no bug found on the on-device screenshot check |
| ✅ | **SparkBarChart** | Tenth component, completing the "spark" family — unlike `SparkLineChart`/`SparkAreaChart`, the web version has no multi-`series` mode for bars at all, so this one doesn't either (single `dataKey`+`color` only). Uses Victory Native's standalone `Bar` (not `BarGroup`/`BarGroup.Bar`, which `BarChart` needs for side-by-side grouping) since there's only ever one series here — `roundedCorners={{ topLeft: 2, topRight: 2 }}` for the top-rounded look, matching the web's `radius={[2,2,0,0]}`. Reuses the same shared `src/internal/sparkTypes.ts` helpers (`normalizeSparkData`, `sparkAccessibilityProps`) as its two siblings. Same dropped `highlighted` hover mode. Shipped with no bug found on the on-device screenshot check |
| ✅ | **ScatterChart** | Eleventh component, first chart in this package where every series owns its own independent point list with its own field names (`xKey`/`yKey`/`zKey`), rather than rows shared across series like every other Cartesian chart here — `CartesianChart` needs one `xKey`/`yKeys` set over a single `data` array, so every series' points are merged into one combined row array first (each row only populates its own series' namespaced `__y_i`/`__z_i` field; Victory Native's `Scatter` itself already skips any point whose `y` isn't a number, so other series' rows render as gaps for free). Bubble sizing (`zKey`/`bubbleRange`) uses `Scatter`'s per-point `radius` callback, scaled by area (matching Recharts' own `ZAxis` `range` semantics: `radius = sqrt(area / π)`). **Real bug found and fixed via the on-device screenshot**: bubble sizes were scrambled — some of the *smallest* z-values rendered as the *largest* bubbles. Root cause, confirmed by reading `transformInputData`'s source: `CartesianChart` sorts its `data` array by `xKey` internally, so `points[key]`'s element order does not match the original (unsorted) merged-row array's order — an index-based `combinedData[idx]` lookup from inside the `radius` callback silently pulled the wrong row's z-value for most points once the sort reordered them. Fixed by matching each point back to its z-value via its own raw `xValue`/`yValue` (which survive the sort intact) through a `Map`, instead of by array position. **General lesson for any future chart merging multiple independent point lists into one `CartesianChart` data array: never assume `points[key]`'s order matches the array you built — `CartesianChart` sorts by `xKey`, confirmed from source, not assumed; match extra per-point data (bubble size, custom colors, labels) by raw value, not by index.** Web's `xLabel`/`yLabel` props dropped — they only ever fed Recharts' tooltip text, which this package doesn't have yet, so they'd have had no visible effect |
| ✅ | **FunnelChart** | Twelfth component, third hand-rolled-on-raw-Skia chart — confirmed no Victory Native primitive by reading its source, proceeded directly without a fresh `AskUserQuestion` this time (the user had already confirmed hand-rolling twice for `RadarChart`/`RadialBarChart`; re-asking a third time for the same category of decision would have been over-asking rather than genuinely uncertain). Each segment is a trapezoid (`SkPathBuilder`, 4 points closed) whose top width is its own value's share of the largest value and whose bottom width tapers into the *next* segment's share — the last segment gets a flat bottom (top=bottom) — reproducing Recharts' actual continuous-taper funnel silhouette rather than a discrete "wedding cake" of independently-sized trapezoids. No legend (the web version has none — `showLegend`/`legendPosition` don't exist on `FunnelChartProps` there either, so this port doesn't invent them). First hand-rolled Skia chart in this package to ship with genuinely zero bugs on the very first on-device screenshot — the accumulated lessons from `RadarChart` (modern `PathBuilder`, not deprecated `Skia.Path.Make()`) and `RadialBarChart` (verify angle/geometry algebra before testing, not by trial and error) paid off directly here |
| ✅ | **ComposedChart** | Thirteenth component, first chart mixing multiple chart *types* (`bar`/`line`/`area`) within one `series` array over a shared `data`/`xAxisKey`, unlike every prior chart where every series shares the same rendering primitive. `CartesianChart`'s children can freely mix `BarGroup`, `Area`, and `Line` in the same render, so no architecture question this time — split `series` by `type` into three lists and render `BarGroup` (all bar-type series together, since `BarGroup` needs every bar it draws as a direct child to compute width/offset) first, then area-type (`Area` fill + a separate `Line` stroke, same pattern as `AreaChart`), then line-type last — a deliberate, documented deviation from the `series` array's own literal order (Recharts interleaves children in JSX order; this port can't interleave bars with other types without breaking `BarGroup`'s width math, so bars always render as the base layer). **Demo-data lesson, not a component bug**: the first on-device screenshot's "bar + area + line" section showed the area series rendered as an invisible sliver flat against the x-axis — root cause was a demo-data mismatch, not a chart bug: `CartesianChart` shares one y-axis domain across every `yKey`, so a `growth` field ranging 8–30 plotted on the same axis as `revenue` (4000–5600) squishes to a hairline (this would happen identically in the web `ComposedChart`, which also has only one shared `YAxis`). Fixed by swapping the demo's `growth` field for a comparable-magnitude `expenses` field — a reminder that any future composed-chart demo must keep every series' value range within the same order of magnitude, since there's no per-series secondary axis in either the web or RN version |
| ✅ | **GaugeChart** | Fourteenth component, fourth with no Victory Native primitive (same category as `RadarChart`/`RadialBarChart`/`FunnelChart`) — proceeded directly on the established hand-rolling preference, no fresh `AskUserQuestion`. Effectively a single-ring simplification of `RadialBarChart`'s already-validated semicircle-gauge geometry (`SkPathBuilder.addArc`, `START_ANGLE=180`/`SWEEP_ANGLE=180`, `strokeCap="round"` on both track and value arcs) — reused the exact sweep-direction convention `RadialBarChart` fixed on-device rather than re-deriving it. Adds `thresholds` (ascending value/color status bands, same "walk sorted thresholds, keep the last one `<=` value" algorithm as the web version) and a centered value+caption drawn as Skia `Text` nodes rather than an absolutely-positioned RN `<Text>` overlay (simpler than layering a second view over the `Canvas`, and this package already draws in-canvas text for every other hand-rolled chart's labels). No RN theme token exists for the web's `--gnome-dim-label-color` CSS var (grepped: zero hits anywhere in the generated theme) — approximated the caption's dimmed look with `theme.windowFgColor` + a Skia `opacity={0.55}` node prop instead of inventing a new theme token for one component. Shipped with zero bugs on the on-device screenshot, continuing the pattern `FunnelChart` started: hand-rolled Skia charts stop finding new bugs once their underlying primitive (arc math, in this case) has already been paid down by an earlier chart in the same package |
